# Live Caption & Translation

实时字幕 + 翻译。麦克风或系统声音进来，一边说一边出字幕和译文。

**两种用法，同一套代码：**

- **纯静态**（推荐分享给别人）—— 部署成静态网页，用户填自己的 API 密钥，密钥只存在他们自己的浏览器里，不经过任何服务器。你零成本、零运维、不碰任何人的密钥。
- **Node 服务器** —— `node server.js`，额外支持腾讯云翻译和扫码文字发言（跨设备同步需要后端）。

---

## 部署成静态网页（零成本）

`public/` 目录就是完整的站点，无构建步骤。

**GitHub Pages**：仓库已带 `.github/workflows/pages.yml`，推 `main` 自动发布。首次需在 Settings → Pages 把 Source 设为 GitHub Actions。

**Cloudflare Pages**：连接仓库，构建命令留空，输出目录填 `public`。

用户首次打开会被引导填写自己的密钥（工具栏「密钥」按钮）。

### 静态模式支持哪些厂商

浏览器能不能直连厂商，取决于对方给不给 CORS 头 —— 这是实测结论，不是推测：

| 厂商 | 浏览器直连 | 原因 |
|---|---|---|
| Soniox（字幕） | ✅ | WebSocket 握手不受 CORS 约束，且配置接受长期密钥 |
| Anthropic（翻译） | ✅ | `access-control-allow-origin: *`，并提供 `anthropic-dangerous-direct-browser-access` 头 |
| 腾讯 TMT / 混元 | ❌ | 完全不返回 CORS 头，浏览器会拦掉响应 |

所以腾讯只能在服务器模式下使用。扫码文字发言同样需要服务器维护临时消息队列，纯静态部署会明确显示为不可用。

> **关于密钥安全**：Soniox 和 Anthropic 的密钥都是单一服务、可计量、可随时吊销的。腾讯给的是 `AKID...` 账号级凭证，能操作该账号下几乎所有云服务 —— **不要把它填进任何网页**，包括本项目的静态版（静态版也根本不提供这个选项）。

## 本地运行

```bash
cp .env.example .env   # 填入你自己的密钥
node server.js
```

打开 <http://localhost:5175>。**没有 `npm install`** —— 零依赖，只用 Node 内置模块。

改完 `.env` 必须重启：它只在启动时读一次。

要让现场手机扫码访问，主持端必须使用手机能访问的地址。正式部署可设置：

```bash
PUBLIC_URL=https://caption.example.com node server.js
```

本地同一 Wi-Fi 测试时，用电脑的局域网 IP（例如 `http://192.168.1.20:5175`）打开主持端；二维码若包含 `localhost`，手机无法访问。

### 扫码文字发言

这个入口面向**失语者、失聪及听障人士**（**non-speaking, Deaf, and hard-of-hearing people**），让无法或不便通过语音参与的人把想表达的内容直接送到现场字幕。

主持端点击「扫码发言」创建一个 6 小时有效的临时房间。参与者扫码后可填写显示名称和最多 500 字的内容，发送后会作为带 `⌨` 标识的段落进入同一字幕列表、滚动、恢复与导出流程。

- 房间只存在当前 Node 进程内，不落盘；重启或点击「结束文字输入」后立即失效。
- 主持端和参与端使用不同的随机凭证；二维码不能读取字幕、密钥或主持端配置。
- 每个手机浏览器独立限流，避免误触刷屏，同时允许多人共用一个二维码。
- 输入内容若配置了外部翻译服务，会沿用当前字幕翻译设置；Soniox 内置翻译仅作用于音频流。

## 字幕和翻译是分开的两层

**字幕（ASR）和翻译是两个独立可换的厂商**，在界面上分别选。这样哪家翻译好就换哪家，不用动字幕那一层。

| | 当前可选 | 说明 |
|---|---|---|
| 字幕 | Soniox / 浏览器识别 | Soniox 便宜且浏览器直连 |
| 翻译 | 腾讯云机器翻译 / Claude Haiku / Soniox 内置 / 不翻译 | 默认取第一个配好密钥的 |

### 为什么 Soniox 内置翻译效果差

不是它模型不行，是**时机**问题：Soniox 在同一条流里边说边翻，句子还没说完就开始吐译文，翻的是**碎片**。碎片翻译天然翻不好，跟换哪家模型没关系。

其他所有 provider 都是**等整句定稿之后**才送去翻译，这是质量差异的主要来源。代价是译文比字幕晚 0.5–2 秒出现（字幕本身不受影响，仍然实时）。

### 加一家新厂商

在 `providers/translate.js` 里实现四个方法，然后注册进 `PROVIDERS` 数组，其余代码不用改：

```js
{
  id: 'volcengine',
  label: '火山翻译',
  needs: ['VOLC_ACCESS_KEY', 'VOLC_SECRET_KEY'],
  available: () => Boolean(process.env.VOLC_ACCESS_KEY),
  async translate({ text, source, target, targetName }) { /* 返回译文字符串 */ },
}
```

前端的下拉框、默认值、错误提示都会自动跟上。

### 备选：腾讯「大模型实时语音翻译」（尚未接入，2026-08-13 调研存档）

如果 TMT 的翻译质量仍不满意，下一步换这个 —— 一条 WebSocket 同时出字幕和译文，翻译走**混元大模型**而非 TMT 统计模型。

- 端点 `wss://asr.cloud.tencent.com/asr/speech_translate/<appid>`
- 鉴权：对查询参数做 HMAC-SHA1 签名，带 `expired` 过期时间 → **服务器签好短时效 URL 给浏览器直连即可，不需要代理音频**（和 Soniox 临时令牌同一个安全模型）
- 音频要求 PCM / 16kHz / 16bit / 单声道 —— **与本项目 AudioWorklet 现有输出完全一致，管线可原样复用**
- `source` 支持 `zh_en`（中英混说）、`zh`、`en`、`ja`、`ko`、`yue`、`id`、`th`、`ru`
- 返回 `source_text` + `target_text`，带 `final` / `sentence_end` 标志 → **只渲染 `final` 结果**即可避免碎片翻译
- 计费 ¥5/小时（后付费），100 小时预付包 ¥480；无免费额度

实测网络延迟（2026-08-13，自澳大利亚悉尼）：

| 端点 | RTT | 丢包 |
|---|---|---|
| `stt-rt.soniox.com`（Cloudflare 边缘） | **12 ms** | 0% |
| `asr.cloud.tencent.com` | 139 ms | 0% |
| `tmt.tencentcloudapi.com` | 134 ms | 0% |

从澳洲访问腾讯慢约 127ms，但链路稳定（0 丢包、抖动 0.25ms）。相对字幕本身约 1.8s 的端到端延迟只多约 7%，体感不明显。

成本对比（¥5/小时 ≈ A$1）：Soniox 字幕 + TMT 翻译约 ¥0.86/小时，统一方案约 ¥5/小时，差约 5.8 倍 —— 个人用量下绝对值都很小。

### 腾讯云配置

控制台 → 访问管理 → API 密钥管理，创建 SecretId / SecretKey，再到「机器翻译」产品页开通服务，填进 `.env`：


TC3-HMAC-SHA256 签名有单元测试（`node test/tc3.test.mjs`），对的是腾讯官方文档里的签名向量。

## 为什么选 Soniox 做字幕

调研了腾讯云、阿里云、Deepgram、AssemblyAI、Google、Azure。选型理由**不是省钱**（个人用量下每小时几毛钱的差别无关紧要），而是这两点：

1. **转写和翻译在同一条 WebSocket 里回来**，不用再接第二家翻译 API。译文按词流式返回，不等整句说完。
2. **浏览器可以直连**。后端用长期 key 换一个 60 秒的临时 key 发给前端，音频**不经过我们的服务器** —— 延迟最低，后端只有一个「发令牌」的接口。

成本对比（按约 7.15 CNY/USD、1.5 AUD/USD 换算）：

| 服务 | 实时转写 | 翻译 | 合计 USD/小时 | AUD/小时 |
|---|---|---|---|---|
| **Soniox** | $0.12 | 同一路流，含 | **$0.12** | **≈A$0.18** |
| 腾讯云 ASR | ¥3.20 ≈ $0.45 | 机翻另计 | $0.45+ | ≈A$0.67+ |
| Deepgram nova-3 | $0.46 | 另接 | $0.46+ | ≈A$0.69+ |
| Google STT v2 | ~$0.96 | 另接 | $0.96+ | ≈A$1.44+ |

约 **3.7 倍**差距（不是我一开始说的 20 倍 —— 那是把人民币当美元比了）。

## 给线上会议加字幕

「音频输入」选 **🔊 标签页 / 系统声音（浏览器捕获）**，点开始后浏览器会弹出选择器 —— 挑一个标签页或整个屏幕，**记得勾上「分享音频」**。

**大多数情况不需要装任何虚拟声卡。** 分两种：

| 声音来源 | 需要什么 |
|---|---|
| 网页里的会议 / 视频（Google Meet、Teams 网页版、YouTube） | 分享该标签页 + 勾选「分享标签页音频」。Chrome / Edge 一直支持，无需安装 |
| 原生应用（Zoom 桌面版等）的系统声音 | Chrome ≥ 141 且 macOS ≥ 14.2 可直接捕获，同样无需安装 |
| 上述条件不满足（旧系统、Safari、Firefox） | 才需要虚拟声卡，见下 |

> Apple 从 macOS 14.2 起才允许第三方应用捕获系统声音，Chrome 141 起支持。低于这个组合就只能走虚拟声卡。

### 退路：虚拟声卡

```bash
brew install blackhole-2ch
```

1. 「音频 MIDI 设置」建一个「多输出设备」= BlackHole 2ch + 你的耳机/音箱（否则声音被 BlackHole 吃掉，你自己听不见）
2. 系统设置 → 声音 → 输出，选这个多输出设备
3. 应用里「音频输入」选 `BlackHole 2ch`

### 布局：原文在上，译文在下

**原文（实际说出口的话）永远是主字幕，在上面、全字重。译文追加在它下面**，字号更小、颜色更淡。译文从不替换原文 —— 否则在自动双向模式下，你说中文时大字会变成英文，看起来就像你的话被顶掉了。

两条滑杆分别控制两行的字号，互不影响；想让两行一样大，拉到同一数值即可。

### 为什么默认是「自动双向」

单向模式有个隐蔽的坑：如果你说的语言**正好等于译文目标**（比如源设 English、译文设中文，但你在说中文），Soniox 会把原文转写得很好，然后返回 **0 个译文 token** —— 等于要求「把中文翻译成中文」。界面上看就是「翻译坏了」，实际是配置问题。

自动双向（Soniox 的 `two_way`）从根上避免了这一点：它检测你实际说的是 A 还是 B，然后翻译成另一种。实测两个方向都通：

```
说中文 → Let's see the results. I don't see any translation available right now.
说英文 → 大家早上好。季度结果超出了我们的预测，营收增长了18%。
```

仍然保留了运行时检测：如果检测到的语言不在配置的两种里（比如说日语），会弹提示并给一键修正按钮。

### 浮窗字幕

⧉ 打开一个 Document Picture-in-Picture 窗口 —— 真正的置顶小窗，可以拖到屏幕任意角落，会浮在 Zoom、Keynote 之上。

实现上是把字幕区**整个搬进**浮窗，而不是复制一份再同步：所有渲染路径继续写同一批节点，一行都不用改，也就不存在两边不同步的可能。关掉浮窗时搬回原位。

字号、主题、显示模式都会同时作用于两个窗口 —— 浮窗是独立 document，CSS 变量必须写进它自己的根元素，否则两边会飘。

### 手机布局

宽度 ≤ 820px 时切换成手机版：字幕占满屏幕，工具栏收进**底部抽屉**（点「⚙ 设置」滑出），开始/停止移到拇指够得到的底栏。

开始按钮是**搬过去**的，不是复制一份 —— 否则两个按钮的状态迟早会不同步。用 `dvh` 而不是 `vh`，浏览器地址栏收起时高度会跟着变；底部留了 `safe-area-inset`，避开 iPhone 的home 指示条。

字号默认更小（原文 26px / 译文 21px）—— 桌面那套是按投屏距离定的，手一臂远看太大。

## 架构

```
浏览器 ──── 麦克风/虚拟声卡
   │         │
   │      AudioWorklet → 16-bit PCM (100ms 分片)
   │         │
   │         └──────── WebSocket 直连 ──────→ Soniox
   │                                            │
   │        ←──── 原文 token + 译文 token ───────┘
   │              （同一条流，translation_status 区分）
   │
   └── POST ./api/token ──→ 本地 server.js ──→ Soniox REST（换 60 秒临时 key）

手机 input.html ── POST 文字 ──→ 临时内存房间 ── 主持端轮询 ──→ 同一字幕列表
```

`server.js` 保持零依赖：发静态文件、签发临时 key、代理翻译，并维护扫码输入的短期内存房间。长期 key 永远不进浏览器，文字房间也接触不到厂商密钥。

**静态模式下整条虚线都不存在** —— 浏览器拿用户自己的长期 key 直接建 WebSocket，翻译也直接打 Anthropic。启动时探测 `./api/config`，404 就自动切到这个模式，同一份代码。

### 分段逻辑

这是全项目最容易出错的地方，值得单独说明。

Soniox 的译文 token **按设计滞后于原文 token**（先出原文，译文随后补上）。所以看到句子结束标记就立刻切段，会导致**每一段的译文都被切进下一段**，整体系统性错位一段。

因此所有边界信号（`<end>` 端点标记、句末标点）都不会立即生效，而是先记下位置、给译文一点时间追上，再切。先到的边界优先；切完立刻重新检查剩余缓冲区，避免漏掉排队的第二个边界。

**切点会吸收随后到达的标点。** Soniox 常常把句末的句号放在下一条消息才发过来，如果按记录的位置硬切，句号会被甩到下一段开头、甚至独自成段。纯标点的片段会并回上一段，也不会被送去翻译 —— 给大模型一个孤零零的「。」再配上下文，它不会翻译，会顺着上下文编一句出来。

**内联翻译时不按从句切。** Soniox 的译文滞后于原文，而且**没有任何信息能表明某个译文 token 属于哪一句原文** —— 唯一让它们配对的机制，就是两者落在同一段里。段落一旦短于滞后时长，译文就会挂到上一段去。所以选 Soniox 内置翻译时，只在句末和端点处切，长度上限也放宽到三倍；换成外部翻译（混元 / Claude）才启用下面的从句切分。

**从句也是切点（仅外部翻译）。** 中文口语常常一逗到底，只认句号会让一整段话挤成一块。所以 `，、；：` 也是切点，但只在当前长度超过阈值后才生效，否则「那个，」会各自成段。长度按「中文字当量」计（汉字记 1，拉丁字符记 0.45），一套阈值同时适配中英文。界面上有短/中/长三档。

### 结束信号必须是空**文本**帧

文档写的是「空帧，二进制或文本均可」，但实测 `ws.send(new ArrayBuffer(0))`（空二进制帧）**Soniox 完全不认** —— 它会继续等音频，20 秒后返回 `error 408 Request timeout`。必须用 `ws.send('')`。

而且发完结束信号**不能立刻 `close()`**：Soniox 会在约 240ms 后把最后一句话的定稿 token 补吐出来，再发 `finished`。立刻关闭 socket 会导致**每次按「停止」都丢掉最后一句**。所以 `stop()` 会等 `finished`（上限 2 秒）再关。

## 已知边界

- **改完代码记得重启 `node server.js`** —— `.env` 只在启动时读一次。另外端口被占时进程会直接 `EADDRINUSE` 退出，若页面行为不对，先 `lsof -nP -iTCP:5175 -sTCP:LISTEN` 看看是不是有旧进程还在跑。
- **腾讯翻译尚未用真密钥跑通**。签名实现有两重验证：官方文档的签名向量逐字节吻合，且用假密钥打真接口时腾讯返回的是 `AuthFailure.SecretIdNotFound`（密钥不存在）而非 `SignatureFailure`（签名错误）—— 说明请求格式已被网关受理。但真实翻译质量和语种覆盖要拿到密钥才能评。
- **腾讯 ASR（做字幕）暂未接入**。它是签名鉴权、没有 Soniox 那种临时令牌机制，浏览器直连会暴露 SecretKey，必须**服务端代理音频**（browser → 本机 server → 腾讯）。这是架构上的实质改动，等确认要用再做。
- **麦克风采集这一段未经真实设备验证**。协议层已用真实音频端到端跑通（合成语音 → 16kHz PCM → Soniox → 转写 + 译文全部正确），浏览器侧的令牌签发与握手也已用真 key 验证，但 `getUserMedia` → AudioWorklet 这一段需要真麦克风才能测。
- **浏览器识别引擎**只在 Chrome / Edge 可用（Safari、Firefox 没有 `SpeechRecognition`），且本身不带翻译；只有在 `.env` 里配了 `ANTHROPIC_API_KEY` 时，才会把每句定稿文本发给 Claude Haiku 翻译。Soniox 引擎不走这条路，它自带翻译且不额外收费。
- 语言下拉里的**粤语（`yue`）未经实测**，其余为 Soniox 文档明确支持的语种。
- 单条 Soniox 流上限 300 分钟；断线会自动重连（指数退避，最多 8 次）并保留已有字幕，音频时间轴会累加以保证 `.srt` 时间戳连续。
- 采集时关闭了浏览器的降噪 / 回声消除 / 自动增益 —— 这些是为通话调优的，会削掉语音细节、也会干扰虚拟声卡输入，流式 ASR 用原始信号效果更好。
- **麦克风需要安全上下文**。`localhost` 天然满足；部署到 GitHub Pages / Cloudflare Pages 也是 HTTPS，没问题。但通过局域网 IP 或 Tailscale IP 以纯 HTTP 访问时，浏览器会拒绝麦克风 —— 这是硬性安全规则，绕不过去。
- **说话人识别**（Soniox diarization）已开启，换人会自动切段并标注 Speaker A/B/C。实测双人对话可正确区分，且同一人再次发言能被认回。
- **字幕自动存本地**，刷新或崩溃后会提示恢复。存储写满时会丢弃最旧的一半再重试，不会静默停止保存。
